# 野狐自动对弈 · 使用说明

一条命令打通：识盘 → 分析 → 落子 → 复查。

---

## 零、桌面版怎么用（老板日常就用这个）

双击桌面 **「野狐自动对弈」**。

界面从上到下五行，从左到右：

| 行 | 控件 | 说明 |
|---|---|---|
| 第一行 | 引擎下拉框 | 序号 1..N 连续，跟 Lizzie 里那套一一对应 |
| 第二行 | 我执 / 规则 / 贴目 | 贴目**可直接键入**，最小 0.5，范围 ±150 |
| 第四行 | 思考时间：**固定** 或 **随机** | 三个框都**可滚可键入**，最小 0.5 秒，范围 0.5~180 秒 |
| 按钮行 | 开启/关闭引擎 · 暂停 · 检查野狐 · 重新标定 | 主键是**开关引擎**，跟暂停完全是两件事；对局中这两个按钮在悬浮球上也有 |

> 「最多手数」「思考上限」已删（老板 2026-10-23 要求）：手数不限，
> 每手想多久完全由「思考时间」决定，不再有两个互相打架的值。

> **数据不会写到 exe 旁边**（2026-10-27 改）。配置和日志统一在
> `%LOCALAPPDATA%\野狐自动对弈\`，exe 放桌面也不会弄脏桌面。
> 想要绿色便携版就在 exe 同目录建个空的 `portable.txt`。

### 三个关键行为

**① 开启引擎后会先等 3 秒才开始下。**
这是留给你关掉其它弹窗、切回野狐的时间。悬浮球日志里有 `3… 2… 1…` 倒计时，
这期间点球上的「暂停」能立刻停住。

**② 对局中主窗口会收起来，屏幕右边出现一个「悬浮球」。**
- 球上有两个按钮：`■ 关闭引擎` ⇄ `▶ 开启引擎`、`⏸ 暂停` ⇄ `▶ 继续`
- 球上常驻**两行日志**：引擎启动进度 / 倒计时 / 当前选点·胜率·目差
- 球按棋盘几何摆到**棋盘之外**（贴所在显示器右边），不压落点；拖空白处能挪
- 停手后球变「已停止」，可以直接从球上再开一局；点右上角 `×` 收起
- **ESC 从 3.1.0 起彻底取消**，不再占用系统按键

**③ 主键是「开启 / 关闭引擎」，跟暂停无关。**
- 主键：`▶ 开启引擎` ⇄ `■ 关闭引擎`
- 暂停键：只管停手/继续，**引擎一直留着**，恢复是 0 秒

| | 停止点鼠标 | 引擎/权重/缓存 | 恢复耗时 |
|---|---|---|---|
| **暂停（悬浮球）** | ✅ 停 | **全留着** | 0 秒，点「继续」立刻能下 |
| **关闭引擎（主键）** | ✅ 停 | 释放（云端还会断会话） | 本机 ~2.5s / 云端 ~8s |

数量级差别：本机 B11 握手 2.5s，云端 fdx 握手 8.3s。

**④ 引擎跑起来后，改不了的选项会变灰。**

判据只有一条：**改了到底生不生效**。

| 选项 | 开启引擎后 | 为什么 |
|---|---|---|
| 我执 / 规则 / 贴目 | 🔒 变灰点不动 | 这三项 `start()` 只在启动那一刻读一次，中途改只改界面、引擎照旧 |
| 思考时间 | ✅ 能调 | 下一手立刻按新时长走 |
| 引擎下拉框 | 🔒 变灰 | 换引擎必须重开 |

关引擎后三项**自动解锁**，改完再开 —— 不用重启程序。

> 以前激进度只是重画界面、根本没下发到引擎：滑条拖回 0，
> 界面显示「标准」，引擎还在用激进档的 7 个参数下棋。
> 现在改成「GUI 只写字段，工作线程下一手开头下发」——
> 顺手解决了另一件事：`set_aggro` 直接发 GTP 命令会和正在分析的
> 工作线程抢同一根管道的应答，轻则丢一手、重则 TimeoutError。

> **2026-11-01：激进度整体删除**（老板原话：「这个没什么用」）。
> 下面这条 ⑤ 是它还在时的排查记录，留着供查考 —— 界面上已经没有这一项了。

**⑤ 大劣势下激进档不会再乱走了（2026-10-27 修，已随选项删除）。**

原来的 bug：白棋被打花（胜率 0.006%）时，激进度一调到 +1 以上，
KataGo 就开始走莫名其妙的点；调成负数反而正常。

根因是**胜率在小数第 5 位饱和了**：

| 局面 | winrate 极差 | scoreLead 极差 |
|---|---|---|
| 均势（空盘） | 0.0168（1.68 点，有区分度） | 0.10 目 |
| 大劣势 | **0.00003**（饱和，分不出来） | **9.68 目**（还有区分度） |

+3 档的胜率容差是 1.2 个点，比 0.00003 大 300 倍 ——
「等价集」直接退化成全部 16 个候选，再按「visits 少 = 对手难准备」
去挑，挑中的恰恰是引擎**最没算透、最容易崩**的那个点。

三条修法：① 目差也进等价判断（它不饱和）② 胜负已定就收手到前 3 名
③「visits 少」的权重从 0.5 降到 0.25。
实测：饱和局面下 +1/+2/+3 从原来的 order 5/8/12 全部收回 order=0，
目差只损失 0.83 目。

### 悬浮球：对局时的唯一操作面（3.1.0 起）

主窗口收起来之后，所有操作都在这颗球上：

| 元素 | 作用 |
|---|---|
| `■ 关闭引擎` / `▶ 开启引擎` | 真关引擎 / 用上次的参数直接再开（不再弹确认框） |
| `⏸ 暂停` / `▶ 继续` | 只停手，引擎和权重都留着，恢复 0 秒 |
| 两行日志 | 引擎启动进度、倒计时、每手选点与胜率目差 |
| 状态点 | 绿=下棋中　琥珀=暂停/等野狐回来　红=出错 |
| 右上 `×` | 只有停手后才出现，点掉只是收球 |

**位置**：`hud.FloatBall.place_beside()` 先算棋盘矩形（有标定用标定，
没标定按「窗口里一块 88% 高的正方形」估），再贴所在显示器工作区的最右边；
右边放不下就退到棋盘左边 → 上方 → 下方，最后才夹回屏内。
**只要可能就不压棋盘** —— 压住落点等于把点击吃掉。

> ESC 热键、`hotkey.py` 的全局注册、`_raise_self()` 弹窗这一整套
> 在 3.1.0 全部下线；`hotkey.py` 文件留着，只是 gui 不再 import。

### 胜率显示是**我方**视角

日志里每手长这样：

```
→ D13　胜率 81.3%　目差 +2.1　(1.15s / 714v / 决策 1.2s)
```

- **胜率是我方胜率**：执白就用白方胜率，执黑自动换成 `1-x`
- **目差正数 = 我方领先**
- 底层数据统一存白方视角，显示时按「我执」翻转，所以切黑白不用改引擎

## 二、引擎怎么选

`--list` 里的 20 项，跟智子客户端「选择要加载的引擎」对话框一一对应。

**强度排序（关键，别按速度选）**

| 引擎 | 权重 | 官方 rating | 说明 |
|---|---|---|---|
| 智子VIP算力 11b 天梯14374 (fdx) | `kata1-tf3-b11c768` | **14594** | **默认，免费，最强** |
| 智子 1x 28b | `b28c512nbt` | 14103 | 要花钱 |
| 本机 b28 | `b28c512nbt` | 14103 | 免费，快 2.5 倍，但弱 490 Elo |
| 本机 b40 | `b40c256` | ~13000 | 老权重 |

老板 2026-10-22 的原话：「11B是最强的水平的AI，28B差很多，智子vip算力FDX是不花钱的里面强，围棋AI不是算越快越强的」

同访问量下 B11 比 B28 高约 **490 Elo**。速度每翻倍只值 150~250 Elo，
拿 10 倍速度换 490 Elo 是亏的 —— 所以默认走云端 B11。

**选引擎的三种写法**

```bash
--engine 1                    # 注册表序号（--list 里的编号）
--engine local:b28            # 精确 key
--engine vip / fdx / 3x       # 别名，模糊匹配
--engine 让2                   # 名字包含，也能命中「智子 3x 让2子对弈」
--pick                        # 交互式，输序号
```

## 三、云引擎的两种接法

```bash
--cloud-mode direct    # 进程内直连（默认，最稳）
--cloud-mode service   # 走 8765 常驻服务
--cloud-mode auto      # 端口开着就用服务，否则直连
```

**为什么默认 direct**：常驻服务需要 spawn 后台进程，父进程组退出、端口被占、
防火墙拦回环……任一环节出问题，前台看到的就是 `ConnectionResetError`。
下一盘棋是单次长任务，多一个进程毫无收益，直连反而少一个故障点。

只有反复调参、或别处（网页/Lizzie）已经开好服务时，才用 `service`。

## 四、当年踩过的坑（改代码前必读）

### 1. 视角：`kata-analyze <color>` 的 color 是「给谁出主意」

**2026-10-22 用五组已知盘面钉死，不要再猜。**

info 里的 `winrate` = **`kata-analyze` 那个 color 一方的胜率**。
不传 color 或传错，算出来的就是别人的胜率。

实测证据（本机 11B，komi 7.5，中国规则）：

| 局面 | 轮走方 | 白胜率 | 黑胜率 | 棋理核对 |
|---|---|---|---|---|
| 空盘 | 黑 | 66.0% | **34.0%** | 黑贴 7.5 目，黑≈34%（老板给的基准） |
| 空盘 | 白 | 99.6% | 0.4% | 黑让一手还照贴 7.5，黑几无胜率 |
| 黑 D16 | 白 | 66.2% | 33.8% | 等于"黑走了一手"，回落到 34% |
| 黑 D16 | 黑 | 0.4% | 99.6% | 黑连走两手，黑大优 |
| 黑D16 白Q4 | 白 | 99.6% | 0.4% | 白连走两手 |

**五行全部自洽**。由此确定：
- 本机这批 cfg（`reportAnalysisWinratesAs` 全被注释）默认 = **轮走方视角**
- 所以 `analyze_gtp(turn=...)` **必须**把 turn 传给 `kata-analyze`
- 落地时统一换成白方视角：`turn=B` 时 `1-x`，`turn=W` 时原值

⚠️ 曾经的错误判据：以为"空盘白先应该 ≈50%"，于是把正确的
99.6% 当成 bug，反过来把代码改错了两轮。**空盘白先是白连走两手，
本来就该接近 100%** —— 老板原话：
「白先等于黑让了一手，黑棋就几乎没有胜率了」。

### 1.5 云端视角：也是「color 一方」，之前的「固定 BLACK」是误判

**2026-10-22 深夜重测，推翻了旧结论。** 旧结论写在上一版 README 里，
说云端「固定 BLACK 视角、不可运行时改」——**错的**，别再用。

实测（智子 VIP fdx，同一进程、同一空盘、只换 color 参数）：

| `kata-analyze` 参数 | 首选 | winrate | 前 5 |
|---|---|---|---|
| 不传 color（老代码） | R16 | 0.3372 | R16 R4 C16 C4 D3 |
| 传 `B` | R16 | 0.3369 | R16 R4 C16 C4 D3 |
| 传 `W` | **C4** | **0.9965** | C4 C16 R4 R16 Q17 |

「不传」与「传 B」**逐位一致** → KataGo 默认按 **B（黑方）** 分析。
所以云的语义跟本机一样：**winrate = color 那一方的胜率**。

`reportAnalysisWinratesAs` 在云端确实改不动（`kata-set-param` 报
`Unrecognized or non-overridable parameter`），但那不是视角来源。

**当初为什么会误判成「固定 BLACK」**：`set_position` 摆了一个
「黑天元 1 子 + 白铺满左上」的盘面，黑子被白棋围死没气，云端回的是

```
Illegal stone placements - overlapping stones or stones with no liberties?
```

而代码只检查回显里有没有 `"Expected"` → **静默通过** → `showboard`
一看还是空盘 → 各种盘面都返回同一个 0.337 / R16，看着就像"固定视角"。
**教训：`send()` 返回任何非空字符串都当失败，不要挑关键词匹配。**

### 1.6 `kata-analyze` 的 `interval` 单位是**厘秒**，不是毫秒

这是老板报的「调 1 秒或 2 秒就不动，必须 3 秒以上」的真凶。

老代码写死 `interval=200` = **2 秒**才吐一轮 info。预算 1~2 秒时
一帧都收不到 → 上层判「没有可下点」→ 直接不下棋。3 秒"能用"
只是因为刚好越过 2 秒这条线。

实测首帧到达时间：

| interval | 200 | 100 | 50 | 20 | 5 | 1 |
|---|---|---|---|---|---|---|
| 首帧 | 2.14s | 1.08s | 0.55s | 0.29s | 0.15s | 0.10s |

现在两边都改成按预算动态算：`interval = 预算秒 × 100 / 6`，
夹在 5~50 厘秒。1 秒预算 → 16（每 0.16s 一轮），3 秒以上 → 50。

修复后逐档实测（本机 11B，真野狐盘面）：

| 预算 | 1s | 2s | 3s | 5s | 8s |
|---|---|---|---|---|---|
| 实际耗时 | 1.19s | 2.19s | 3.19s | 5.19s | 8.20s |
| 帧数 | 6~9 | 11~12 | 12 | 12 | 12 |

### 1.7 GTP `send()` 的快照必须在 `write` **之前**取

老板报的「经常显示连接失败超时」根因，**2026-10-22 在 `komi` 命令上抓到现场**。

老写法是先写命令、再在 `_read_reply()` 里 `idx = len(lines)` 取快照。
`komi` / `boardsize` / `name` 这类命令引擎几乎瞬间就回，应答可能在
**取快照之前**已经被读线程放进 `_lines` → 快照把它圈掉 → 永远等不到
→ 30 秒后抛 `TimeoutError: GTP 应答超时：[]`。

纯看 GIL 调度，所以是「经常」而不是「必然」，特别难缠。

正确顺序：**先取快照 → 再写命令 → 从快照往后读**。
`local_engine.py` 和 `zhizi_cloud.py` 两边都已改。

### 2. 摆盘：`set_position` 不管轮次，`play pass` 会毁掉胜率

三次试错全记录（别走回头路）：

| 做法 | 轮次 | 副作用 |
|---|---|---|
| `set_position B D4 W D16` | ❌ 恒为黑先 | 只摆子，`showboard` 永远 `Next player: Black` |
| `clear_board` + `play` 逐手 + `play B pass` 调轮次 | ✅ | ❌ **pass 被当成停一手**，MoveNum+1，引擎认为进入终局 → 空盘报「白 99.6% / +14 目」 |
| **`loadsgf`（本机现用）** | ✅ | 无。SGF 头写 `PL[W]`+`AB`/`AW`，MoveNum 仍是 0 |
| **`set_position` + `play B pass`（云端现用）** | ✅ | MoveNum 变 1，但**胜率不受污染**（实测空盘黑先 0.3372 → pass 后 0.3325） |

云端为什么不能 `loadsgf`：SGF 文件在**本机**，云引擎经 SSH 隧道在远端，
读不到本地路径。所以云端只能用 `set_position` + `play B pass`。
本机 `set_position` 走 sgf 全文内联，无此问题。

`set_position` 现在每次写一个临时 sgf，并用 `_next_player()` 断言的轮次，
断言失败直接抛异常（轮次错 = 全盘胜率错，绝不能静默放过）。
**云端 `set_position` 的回显任何非空字符串都抛异常**（见 1.5）。

顺带两个坑：
- `play W pass` 只在**真的轮到白**时才推进轮次，传错方会被静默忽略
- `kata-analyze` 一条 info 里塞 **189~273 个候选**，而它们的
  `winrate`/`scoreLead` **全都是根节点值、一模一样**；
  排序请用 `order` 字段（0=首选），**别按 winrate 重排**

### 3. `maxVisits` 写死在 cfg 里，`kata-set-param` 改不动

Lizzie 的 cfg 里 `maxVisits = 500`。`kata-set-param maxVisits 1200`
返回空串、不报错、**但引擎照旧按 500 封顶**。
后果：每个候选只分到几十次访问，info 里还是网络直觉值。

解法：启动时加
```
-override-config maxVisits=10000000,maxTime=100000.0
```
日志里能看到 `Config override: maxVisits = 10000000` 才算生效。

### 4. `kata-analyze` 残留污染

上一轮被终止后，引擎还在吐 `info`，读线程晚一步收进来会当成本次结果。
症状：同一盘面「白先 33.5%、黑先 68.0%」自相矛盾。
解法：`analyze()` 前后各发一次 `name` 做 `_barrier()`。

### 4. 窗口定位不能靠标题

实测标题是 `> [高级房1]`、`对局研究 - [第119手]`，早期按「号房间/对弈中」
匹配全失效。现在按进程名 `foxwq.exe` 反查 PID。

### 5. 棋盘几何必须自动标定

写死的 `(297.5, 95.5)/71.0556` 是按 2560×1531 量的，换到 938×942 全错。
现在 `calibrate()` 用**暗像素投影找网格线**，19/19 条线回归，
实测 `x0=95.0 y0=78.0 step=38.016`。

> 木块边界 + 半格推算会偏 8px（第 18 条线跑到木色区外面），网格线法才准。

### 6. 判色用面积占比，不用平均亮度

交叉点正中就是网格线（lum≈48），平均值被拉低，空点能测成 110 以下 → 判成黑子。
改成圆盘内三分类面积统计：`dark` / `white` / `wood`，用色偏区分
（木色 R−B≈90~110，白子 R−B≈15~25）。

> ⚠️ **但整圆平均会被「中心标记」污染**（2026-10-22 实盘踩到）
> ------------------------------------------------------------
> 野狐在一颗**白子**上画了居中的黑色方块（边长 0.50 格），整圆暗占比
> 从 0% 冲到 **45.9%**，顶穿了「暗 > 42% 判黑」的阈值 →
> **白子读成黑子，整盘少一颗白多一颗黑**。
>
> 现在 `classify()` **身份只由外圈环带（55%~100% 半径）决定**，
> 中心区域不参与黑白判定。标记盖不到外圈，所以怎么画都不会翻。
>
> 实测环带亮度（O14 那颗被方块盖住的白子）：
>
> | 环带 | 0-40% | 40-65% | 65-88% | 88-100% |
> |---|---|---|---|---|
> | 被方块盖的白子 | 0 | 37 | **175** | **205** |
> | 正常白子 | 228 | 224 | **217** | **207** |
>
> 外圈两档几乎一样（175/205 vs 217/207）→ 判白正确。中心 0 vs 228 → 只是「有标记」。

### 6.5 轮走方：看最后一手的反色标记（老板提的办法）

野狐在**最后一手**的棋子上画一个**反色三角**，这正是大多数对弈平台的通用做法：

| 最后一手 | 标记 | 反色占比 | 四象限分布 |
|---|---|---|---|
| 白子 | 黑三角（右下角） | 20.4% | 0 / 0 / 0 / **100** |
| 黑子 | 白三角（右下角） | 20.4% | 0 / 0 / 0 / **100** |
| （干扰）白子 | **居中**黑方块 | 39.1% | 34 / 24 / 24 / 17 |

`find_last_move()` 三条判据同时成立才算：

1. 反色像素占比 > 5%（有东西）
2. 反色像素集中在**单一象限** ≥ 62%（是三角不是方块）
3. 占比 < 60%（不是整个棋子被换色）

> **为什么必须查象限**：居中方块的四象限是 25/25/25/25，真三角是 0/0/0/100。
> 靠这一条把界面元素和真标记分开，否则方块会被当成「最后一手」。
>
> **标记 vs 标题**：两者结论相反时信标题（纯文本不受渲染影响）；
> 标题没写「第N手」时才单独信标记。标记的价值是**比标题刷新快**
> ——野狐落子后标题有时要 0.3~1s 才更新，标记是立刻画上去的。

### 6.6 桌面 .bat 必须存成 CRLF + GBK（双击闪退就是这个）

**症状**：双击 bat → 黑窗口刷一屏「xxx 不是内部或外部命令，也不是可运行的程序」→
「请按任意键继续」→ 按键后消失，程序没起来。

**根因**：文件被存成了 **UTF-8 + LF**。cmd.exe 两条硬要求：

| 要求 | 不对时的表现 |
|---|---|
| 换行必须 **CRLF**（`\r\n`） | 裸 LF 被当行内字符 → 整个文件当一整行 → 报几十条「不是内部或外部命令」 |
| 非 ASCII 必须当前代码页（中文 = **GBK/936**） | UTF-8 中文变乱码，`rem` 注释行可能吃掉后续命令 |

**Write 工具写 .bat 必然踩这个坑**（它按 UTF-8 + LF 存）。解决办法：

```bash
# 改 bat 一律走这个脚本，别直接用编辑器存
python _fix_launcher.py
```

`_fix_launcher.py` 直接写二进制（`"\r\n".join(...).encode("gbk")`），
写完会自检：**裸 LF 必须为 0**、GBK 必须可解码。

> 顺带提醒：`bat` 里用 `start "" "%PYW%" "%GUI%"` 启动 pythonw 后立刻 `exit /b 0`。
> 如果外面用 `subprocess.run(capture_output=True)` 调这个 bat，会**死锁**
> —— pythonw 继承了管道句柄且常驻不退出，run() 一直等 EOF。
> 测试时给 `stdout=DEVNULL` 就行。

### 6.7 pythonw 下崩溃是静默的 —— 必须装 excepthook

`pythonw.exe` 没有控制台，未捕获异常**一个字都不显示**，进程直接消失。
表现和「闪退」一模一样，但其实是代码报错。

`gui.py` 现在装了 `sys.excepthook`：

- 崩溃时写 `GUI-崩溃日志.txt`（同目录，附完整 traceback + 时间戳）
- 同时弹 `messagebox` 告知，不会让人对着空桌面猜

### 7. 落子前必须抢前台

点击打的是**屏幕绝对坐标**，不认窗口层级。野狐被挡住时点下去会落到别人身上，
轻则白点，重点到「认输」直接输棋。
`play_move()` 现在会 `SetForegroundWindow` 并核对 `GetForegroundWindow`，
抢不到就**拒绝点击**。

### 8. 落子复查必须严格

老逻辑「盘面变了就算成功」有坑：对手的手和我的点击撞在同一秒时，
对手落完盘面就变了，我这边直接判成功 → 下一手按错误轮次算，还白丢一手。
现在只认「我要下的那个点有我的子」。

### 9. 落子点击带**微随机偏移**（2026-11-01 加的底层规则）

老板原话：「鼠标点击的时候随机偏移少许（微微随机偏离，不要影响落子位置，
不用做成选项，写成底层规则就可以）」。

老代码每手都点在交叉点的**精确中心**：同一个点在一局里出现两次，坐标一位不差；
两局之间也一样。这是机器最容易露馅的地方。

现在 `play_move()` 在算完屏幕坐标后加一个圆盘内的随机偏移，
三条约束全部写死在 `fox_board.py` 顶部，**不做成选项**：

| 约束 | 值 | 为什么 |
|---|---|---|
| 偏移半径 | `min(2.2px, 格距×6%, 格距/4)` | 「微微」 |
| 落点不变 | 19 路格距 38px → 半径 2.2px，是**半格的 12%** | 野狐按「最近的交叉点」判定 |
| 取样 | 圆盘内均匀（半径开方） | 方形取样会把对角偏移放大 √2 倍 |

实测（`python _test_click_jitter.py`）：19 / 13 / 9 路各 200 次点击，
把点击坐标反算回最近交叉点，**200/200 全部仍是原来那个点**；
200 次的像素坐标有 200 种不同取值。

> 它只改「点在哪」的最后一公里，不动标定、不动复查、不动轮次判断 ——
> 复查读的是 `b2[y][x]`，跟偏移无关。

### 12. 点击落到了**别的窗口**上 —— 「点了没反应」的第二个真凶（2026-11-02）

**现象**：日志里每手都是

```
落子 R16 2.5s 内未见生效；盘面上没有新子（点击坐标 (1490, 361)）
```

而且换着点、重试十几次都没用。盘面读得对、坐标算得对、点击也确实发出去了。

**根因**：`activate()` 只保证「野狐是前台」，但**前台 ≠ 落点归你**。
只要野狐的棋盘上压着任何别的窗口（本程序自己的窗口、聊天工具、置顶小工具），
`mouse_event` 点的是**那个窗口**，野狐一个字节都收不到。

现场用 `WindowFromPoint(1490, 361)` 一查就露馅了：返回的是
`Chrome_RenderWidgetHostHWND`（浏览器/聊天窗口），根本不是野狐。

还有一个自己给自己挖的坑：暂停时 `_raise_self()` 会把本窗口**置顶 300ms**
再撤销。那个撤销是 `after(300, …)`，主线程一忙就可能被吞掉 ——
窗口永久置顶，之后每一手点击都落在自己身上。

**修法**（`fox_board.play_move` 的判据整个换掉）：

> **2026-11-02 定稿：开下之后自动最小化本窗口。**
> 老板原话：「不用保持弹窗了，还是落子就自动最小化弹窗好了」。
> 引擎就绪、开始落子的那一刻 `iconify()`；收工（done/error）自动放回来。
> 这样窗口**永远不可能**压在棋盘上。
> （3.1.0 起暂停也不再弹主窗口 —— 状态改由悬浮球显示，见上文。）

| 落点属于谁 | 处理 |
|---|---|
| 本来就是野狐 | **直接点**，不抢焦点、不抬窗口（本程序窗口不用最小化） |
| 是别的窗口 | 先把野狐硬推到 z 序最上层（`SetWindowPos(HWND_TOP)`），再确认一次 |
| 还是别人的 | **这一手不点**，日志报一次「落点被挡住：某某窗口」 |

配套：

- 暂停置顶改成**两段撤销**（300ms + 1200ms），并把「开跑前先撤置顶」写进 `start()`
- 同一类错误 60 秒只报一次（`Auto._log_once`）
- ESC 加看门狗：引擎启动中也能暂停；全局热键掉了（线程退出）自动补注册

> 验证：`window_at_point()` 在真机上逐点核对过（野狐棋盘 → `CChessboardPanel`，
> 被聊天窗口盖住时 → `Chrome_RenderWidgetHostHWND`），判据可靠。

### 11. 「落子 2.5s 内未见生效」= 轮次判断信了滞后的标题（2026-11-01 现场）

**现象**：引擎跑起来，读盘正常，日志一行行往下走，但一手都落不出去：

```
[第 1 手] 黑3/白3 该白走（固定 0.5s）      ← 6 个子却轮到白？矛盾
→ D15  胜率 18.0% …                      ← 引擎确实算出了着法
落子 D15 2.5s 内未见生效                   ← 野狐压根不认这一手
→ 连换 D14 / R14 / Q3，全部「未见生效」→ 收工
```

**根因**：野狐落子后，标题里的「第 N 手」要 **0.3~1s** 才更新，
而最后一手的反色三角是**立刻**画上去的。两者打架时老逻辑一律信标题
（`side_to_move` 的注释里写着「稳定性优先」），于是程序以为轮到自己，
点下去的时候野狐那边还停在「不是你的回合」—— 点击被**静默无视**，
表现就是「点了没反应」。连续几次之后触发「连续 8 手落不出去」收工。

**修法**（`Auto._turn_settled`）：

| 情况 | 处理 |
|---|---|
| 标题和标记一致 | 直接用 |
| 两边打架 | **等标题追上**（只读窗口标题，不截图，最多 1.2s） |
| 等不到 | 按**最后一手标记**走（盘面实时，标题不实时） |

顺手补了两条诊断，下次再出问题一眼能看懂：

- 落子失败时打印**点击坐标**（`点击坐标 (1078, 716)`）
- 打印这一手之后**新出现的子**（`新出现：K10黑`）；一个都没有 =
  野狐没接受这一手（不是点歪），日志会直接提示「轮次不对/违规」

> 验证：修完后用 CLI 在真野狐上连下 24 手，全部「稳定复读 → 落子 → 复查通过」；
> 点击坐标经 `WindowFromPoint` 核对，正好落在 `CChessboardPanel` 上。

### 10. 在 DSH 工作区里打出来的 exe 会继承「低完整性」标签（2026-11-01）

**症状**：exe 双击能开、界面正常、引擎能连，但——

- `--selftest` 最后一行是「写入失败：[Errno 13] Permission denied: selftest.log」
- 设置改了不保存（下次启动回到默认值）
- 没有对局日志、没有 `GUI-崩溃日志.txt`

**根因**：`C:\Users\Administrator\Documents\deepseek-harness\default-workspace`
这个工作区目录带 **低完整性标签**（`S-1-16-4096`，禁止向上写）。
`dist/` 是它的子目录，PyInstaller 在那里产出的 exe **继承**了这个标签。
带标签的 exe 一启动，进程本身就是低完整性 —— 而 `%LOCALAPPDATA%` 下的
文件是中等完整性，低完整性进程写它一律 `ACCESS_DENIED`。

资源管理器、任务管理器上看不出任何异常，所以特别难查。
对照实验（同一份源码、同一台机器）：旧的 10-27 exe 无标签、写得进；
新打的 exe 有标签、写不进。

**修法**：打包最后一步

```bash
icacls dist/野狐自动对弈.exe /setintegritylevel Medium
```

已经写进 `build_exe.py`，**以后一律用它打包，别手敲 PyInstaller**：

```bash
python build_exe.py              # 打包，产物在 dist/
python build_exe.py --install    # 打包 + 备份旧桌面 exe + 换新的
```

脚本会读回标签核对（还是 `S-1-16-4096` 就报错退出），并打印大小 / MD5。

### ② 修「不下子报错」—— 抢不到前台不等于不能点

v3.0.3 的落子流程是「先抬野狐 → activate() 失败就拒绝点击」。

Windows 前台锁（foreground lock）经常不让它 `SetForegroundWindow`。
结果就是每一手都在 `play_move` 里被拒 —— 日志一行
「野狐不在前台，拒绝点击（防误点）」，一手都下不出去。

**修法**（`fox_board.play_move`）：

- 抬窗口降级成**尽力而为**（另加 `AttachThreadInput` 合法通道）；
- 真正的门槛只有一个：`window_at_point(落点) == 野狐`；
- 落点确实被别的窗口压住 → 仍然**绝不点**，日志报「落点被挡住」；
- 验收脚本 `_test_click_gate.py` 把这两条都钉住了。
